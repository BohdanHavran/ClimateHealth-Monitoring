# Технічний аудит та перший етап стабілізації

Основна база: `Диплом 2.0`. Початкова перевірка — статичний аналіз вихідних Python- і HTML-файлів. Актуальні результати прогонів та середовища наведено в README й звіті тестування; наявність функції в коді не доводить її працездатності з реальними залежностями.

## Початковий стан

`climat.py` містив Flask-маршрути, роботу з MySQL через PyMySQL, OpenWeather, обчислення 27 нечітких правил scikit-fuzzy, побудову графіків Matplotlib, імпорт GeoNames і кеш HRI. Jinja2-шаблони надають ручний, погодний та DB-аналіз, карти Leaflet та інформаційні сторінки. `app.py` є незалежним Streamlit-прототипом для CSV; автоматичного імпорту цього CSV у `climate_data` немає. Архів `course.zip` зберігає первинні копії — це важливо з огляду на виявлений секрет; його не слід публікувати або включати в образ.

Git у початковій директорії відсутній. Первинних автоматизованих тестів і переліку залежностей у ній не було. За межами початкового каталогу існував набір ізольованих характеризаційних тестів; його старе очікування про прийняття NaN після виправлення застаріле. MySQL-схема `climate_data` у вихідному Flask-коді припускається, але не створюється; наявність і вміст серверної БД самі по собі статичним аналізом не підтверджуються. Оригінальна копія `climat.py` збережена за межами проєктного каталогу в контрольованому локальному архіві аудиту; вона містить секрет і не призначена для публікації.

SQL-значення в досліджених запитах передаються параметрами PyMySQL; твердження про SQL-ін’єкцію без доказу не робиться. Винятки тепер не повертають рядок драйвера клієнту. API-ключ передається провайдеру через параметризований запит, проте транспортні/проксі-журнали поза застосунком теж потребують контролю.

## Конфігурація та перевірка

Прямі залежності зафіксовано в `requirements.txt` для Python 3.12; це не повний транзитивний hash lock. Версії Flask 3.1.3, PyMySQL 1.2.4, requests 2.34.2, gunicorn 27.0.1 перевірено за сторінками [Flask](https://pypi.org/project/Flask/), [PyMySQL](https://pypi.org/project/PyMySQL/), [requests](https://pypi.org/project/requests/) та [gunicorn](https://pypi.org/project/gunicorn/). Аудит вразливостей, сумісність усіх транзитивних пакетів та Linux-збирання мають підтверджуватися окремим CI-прогоном.

`DB_PASS_FILE` має пріоритет над `DB_PASS`: файл читається в UTF-8 не більше 4096 байт, порожні й некоректні значення відхиляються. `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_NAME` задають MySQL; `OPENWEATHER_API_KEY` не має вбудованого резервного значення. Жоден режим не передбачає неявного повернення синтетичних медичних значень. `tests/test_routes.py` ізолює HTTP-контракти mock-об’єктами і не підміняє повну MySQL/API-інтеграцію. Реальні факти запуску й перевірки слід звіряти з фінальним звітом.

Ризики, які залишаються: тестування браузера й пристроїв, доступність/якість MySQL-даних, розмежування реальної радіації й оцінки, неавтентифіковані публічні маршрути, rate limiting, TLS, діагностика й відновлення БД, повний SBOM і SCA. Генерація прогнозу здоров’я потребує законно доступної цільової змінної та незалежної оцінки; у поточному CSV її немає.
