# Вибір технологічного стеку

23.11.2026. Статус: **спроєктовано**. Порівняння якісне; порівняльні навантажувальні вимірювання цих фреймворків на цьому застосунку не проводилися. Рішення для першого етапу — стабілізувати Flask, а не змінювати одночасно мову, сервер і інтерфейс.

## Backend

| Варіант | API, валідація, безпека, тести | MySQL і ML API | Ресурси / міграція / підтримка |
|---|---|---|---|
| Flask | WSGI; валідація й OpenAPI потребують явного шару; test client; безпечне розгортання через WSGI/proxy | PyMySQL уже застосовано; можливий SQLAlchemy; HTTP до окремого ML | Найменше перенесення; потрібне розділення функцій і контрактні тести; продуктивність не виміряна |
| FastAPI | Типізовані схеми, OpenAPI, ASGI; async не прискорює CPU-обчислення автоматично | SQLAlchemy/MySQL; зручно для Python inference | Помірна міграція маршрутів, шаблонів і sync БД; хороший кандидат окремого ML API |
| Django + DRF | ORM, міграції, права, serializers, тестування; керовані конвенції | Django ORM підтримує MySQL; зовнішній ML через HTTP | Більше вбудованих підсистем, але значне перенесення без підтвердженої потреби в admin/auth-платформі |
| NestJS | TypeScript, modules, pipes/guards, тестування й Swagger-пакет | MySQL через сумісний ORM; Python ML залишається окремим | Єдина TS-мова з UI, але повне переписування Python бізнес-логіки і ще одне середовище підтримки |
| Go + Gin | Маршрути, binding, middleware; специфікацію й політики потрібно організувати | MySQL driver/sql; виклик Python ML через HTTP | Компіляція й потенційно невеликий runtime, проте перенос fuzzy/графіків і висока вартість зміни мови |

Масштабування кожного варіанта потребує stateless-запитів, пулу/лімітів з’єднань, правильного кешу й вимірювань. Жоден фреймворк не забезпечує безпеку чи низьку вартість сам по собі. Docker підтримує всі варіанти; це не критерій перемоги.

**Рекомендований основний backend: Python 3.12 + модульний Flask, MySQL, спочатку PyMySQL; SQLAlchemy/Alembic — наступне рішення для репозиторіїв і міграцій.** Спочатку зберігаємо API та правила, додаємо тести й прибираємо критичні дефекти. Немає доведеної продуктивнісної причини міняти Flask. Для окремого ML-сервісу рекомендується FastAPI + PyTorch, але зараз є тільки контракт і прототип валідації без HTTP/моделі.

Джерела: [Flask production](https://flask.palletsprojects.com/en/stable/deploying/), [FastAPI features](https://fastapi.tiangolo.com/features/), [DRF](https://www.django-rest-framework.org/), [NestJS](https://docs.nestjs.com/), [Gin](https://gin-gonic.com/en/docs/). Висновок про доцільність міграції — інженерна оцінка для цього проєкту, а не результат benchmark.

## Frontend

| Варіант | Можливості та вартість |
|---|---|
| Jinja2 + JS | Наявні сторінки; найменше змін і один runtime; складніше підтримувати взаємозалежний стан карти/фільтрів/прогнозів у великих inline scripts |
| React + TypeScript + Vite | Типізовані компоненти та статична збірка; підходить інтерактивному dashboard без обов’язкового SSR; потрібні нові API-контракти й клієнтські тести |
| Next.js | React із маршрутизацією й можливостями серверного рендерингу; окремий Node runtime потрібен для серверних функцій, які для цього dashboard поки не обґрунтовані |
| Vue + TypeScript | Порівнянна SPA-архітектура з компонентами й реактивністю; повноцінна альтернатива React, переваги за швидкодією тут не виміряні |
| Nuxt | Vue framework з SSR і серверним контуром; корисний за таких вимог, але додає непотрібну зараз серверну відповідальність |
| Svelte / SvelteKit | Компіляторні компоненти й варіанти static/SSR; доцільна альтернатива, але потрібне перенесення та перевірка інтеграцій |

**Рекомендований цільовий frontend: React + TypeScript + Vite, статична збірка за reverse proxy.** Реалізацію SPA не розпочато на першому етапі; Jinja2 залишено до появи API v1 та тестів. Причина вибору — складність узгодження карти, часових фільтрів, джерел, статусів і порівняння прогнозів. Це не твердження, що React універсально швидший. Непотрібний зараз SSR не додається.

Джерела: [React](https://react.dev/learn/creating-a-react-app), [Next.js](https://nextjs.org/docs/app), [Vue](https://vuejs.org/guide/introduction.html), [Nuxt](https://nuxt.com/docs/4.x/getting-started/introduction), [SvelteKit](https://svelte.dev/docs/kit/introduction). Рекомендація React починати з framework врахована; Vite SPA обрано через окремий backend та відсутність вимог SSR/SEO.

## Карти й графіки

| Бібліотека | Рішення |
|---|---|
| Leaflet / React-Leaflet | Зберегти Leaflet для поточних точок і heatmap; у SPA — сумісні React-Leaflet/React версії. Перед міграцією перевірити peer dependencies, не брати prerelease автоматично |
| MapLibre GL JS | Кандидат для векторних тайлів/великих географічних шарів; потреби й benchmark поки немає, заміну відкласти |
| Recharts | Прості React-графіки; добрий менший варіант для невеликого dashboard |
| Apache ECharts | Рекомендований для інтерактивних часових графіків, zoom і кількох серій; фактичну швидкодію перевірити на обраних обсягах |
| Matplotlib | Залишається для наявних зображень; не видається за інтерактивний клієнтський графік |

Джерела: [Leaflet](https://leafletjs.com/reference.html), [React-Leaflet](https://react-leaflet.js.org/docs/start-introduction/), [MapLibre](https://maplibre.org/maplibre-gl-js/docs/), [Recharts](https://recharts.github.io/), [ECharts](https://echarts.apache.org/en/index.html).

MySQL є остаточним обмеженням для всіх компонентів. Друга СУБД, окремий broker/cache server і складна оркестрація на цьому етапі не потрібні.
