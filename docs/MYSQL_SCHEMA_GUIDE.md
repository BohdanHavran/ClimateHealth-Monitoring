# MySQL: схема та мінімальні права

## Стан другої фази

У `climat.py` більше немає `CREATE TABLE`. Читання impacts/cache/населених пунктів не виконує DDL або commit. Конфігурація `DATABASE_WRITES_ENABLED=False` задана в коді й не вмикається через `.env`; кожне з’єднання застосунку починає `START TRANSACTION READ ONLY`. Імпорт і seed відмовляють до SQL, запис кешу пропускається. Свіжа погода кешується тільки в обмеженій пам’яті процесу. Наявні таблиці, історичні дані та кеш не змінювалися.

`climate_health/repository.py:schema_report` перевіряє наявність потрібних таблиць і стовпців через information_schema. Це мінімальна перевірка проєкції читання, не повна перевірка типів, індексів, медичного змісту чи походження записів. `/api/v1/schema` повертає 503 за несумісності, нічого не створює. Тести перевіряють сумісний і неповний набір, SELECT-only операції, відсутність DDL у legacy-модулі та відмову записів.

## Контрольоване керування схемою — підготовлено, не виконано

SQL baseline вже зберігається у `infrastructure/docker/mysql-init/001_schema.sql`; це самостійний SQL-файл, його читання не потребує Docker. Він містить створення чотирьох таблиць для **нової порожньої схеми** та INSERT IGNORE довідкових описів. Цей baseline **не є міграцією наявної climate_db**, не застосовувався й не повинен автоматично запускатися з HTTP/CLI при старті. `CREATE IF NOT EXISTS` не перевіряє сумісність уже наявних колонок і не заміняє контроль змін.

Порядок для адміністратора після окремого дозволу:

1. Зафіксувати фактичну схему через SHOW CREATE TABLE/information_schema, обсяги й необхідні індекси; зберігати знімок без секретів окремо від даних.
2. Отримати узгоджений backup `climate_db`, перевірити шифрування, права доступу, checksum і відновлення **в окремому погодженому середовищі**. На цьому етапі backup/restore не виконувалися.
3. Підготувати пронумерований SQL patch від реального snapshot: preconditions, очікувана зміна, перевірка після, оцінка блокувань і окремий recovery plan. Для MySQL DDL може робити implicit commit; rollback транзакції не гарантує відкату схеми.
4. Перевірити patch на відновленій копії, переглянути diff, погодити конкретний SQL і час. Зафіксувати checksum виконаного patch у контрольованому журналі; автоматичної migration table у робочій БД зараз немає.
5. Застосувати лише погоджений patch окремою адміністративною роллю. Runtime не отримує CREATE/ALTER/DROP/GRANT. Перевірити reader/API, backup і сумісність попередньої версії застосунку.

Зміни типів `climate_data`, додавання індексів/часу/території не припускаються як уже потрібні: спочатку визначаються за вимогами й реальними даними. У фазі 2 немає нової схеми, SQL patch або аккаунта, застосованих до сервера користувача.

## Окремий MySQL account — лише план

Початковий режим: окремий `climate_reader` із SELECT **лише** на `climate_db.climate_data`, `ua_places`, `hri_cache`, `hri_impacts`; host обмежити фактичним IP клієнта/підмережею, узгодити TLS. Пароль створити адміністратором, зберігати тільки у локальному secret file/env, не в SQL-репозиторії. Information_schema показує доступні користувачу метадані автоматично; глобальні SELECT/PROCESS не потрібні.

Після погодження записів кешу — інша runtime роль із SELECT/INSERT/UPDATE тільки `hri_cache`. Не давати DELETE/DDL/GRANT. GeoNames import та seed — окрема адміністративна операція. Root допустимий зараз лише для погоджених read-only діагностичних запусків, не для постійної роботи. CREATE USER/GRANT/REVOKE не виконувалися. Успіх read-only тесту з root не доводить перевіреності майбутньої обмеженої ролі.
